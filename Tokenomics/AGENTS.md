# Maxshot Tokenomics agent onboarding

**Purpose:** Start here when developing Maxshot's unified Gateway and MAX/AIT product. This is a guide for agents working in this repository, not the customer-facing `SKILL.md` or setup instructions for an external agent using the Gateway API. It is not a new product specification or approval of token launch terms. For conflicting product documents, use the [development handoff index](./DEVELOPMENT_HANDOFF_INDEX.md) and the owning document it names. Preserve both read-only sources: [token PRD](./MAXSHOT_Tokens_PRD_v1.0(read%20only).md) and [marketing deck](./maxshot_marketing_narrative_gtm_playbook(read%20only).pptx).

## 1. What Maxshot is building

Maxshot is building a multi-model inference Gateway with one customer account for Chat, Studio image/video generation, API and external-agent calls, provider discovery, funding, subscription allowances, Credits and Usage. The agreed production design selects the lowest quoted provider cost among offerings qualified for the customer's chosen model, authorizes a hard maximum charge before dispatch, meters the actual serving offering and settles the account once. An unpinned request may use at most one same-model provider fallback after an allowed failure before customer-visible output; an explicitly pinned offering has no automatic fallback. Customers can use ordinary funded service without holding MAX or AIT. This repository simulates these flows; it does not prove that the production Gateway implements them.

`gateway.maxshot.ai` is the intended single application interface. The former `app.maxshot.ai` token and Vault experience is being folded into it. Vault deposits/withdrawals retain their existing contract behavior; Portfolio summarizes Vault deposits, token positions and Gateway balances. The old Mint, Dashboard, Staking, Markets and Agents Factory portals are retired as separate app destinations. The unified sidebar is **Portfolio, Chat, Studio, Credits, Tokens, Providers, Vaults, Referrals**. Tokens opens the MAX & AIT area; API keys live in Profile → Developer settings; Usage lives in Credits. Starters and Playground remain hidden. See [unified-app decisions](./MAXSHOT_Unified_Gateway_App_Decisions.md) and the [UI reference map](../frontend/TOKEN_UI_REFERENCE_MAP.md).

The Gateway/subscription foundation precedes the unified MAX/AIT release. The latter adds gated on-chain token operations and a separately funded off-chain AIT Earned Credit program. The agreed **external-agent integration path** must let a developer or creator follow versioned, verified instructions to authenticate with scoped Gateway credentials, discover permitted models, make a bounded funded call and inspect Usage. Its live URLs and actions still require verification; this file is not that integration guide. A managed Agent object, one-Agent-per-account rule, Agent Wallet, Agent Factory and mandatory MCP endpoint are not approved Tokenomics-release requirements. See the [release scope matrix](./RELEASE_SCOPE_MATRIX.md).

## 2. Token and balance model

| Item | Role and current design | Important boundary |
| --- | --- | --- |
| **MAX** | Fixed maximum supply of 1 billion, fully minted on Ethereum into purpose-specific custodian wallets at genesis. Any transferable ERC-20 MAX may be locked on Ethereum to mint AIT. MAX uses 18 decimals and LayerZero routes among Ethereum, Base, Arbitrum One and Robinhood Chain, including direct destination-chain routes. | Bridging moves existing global supply; it is not new issuance. MAX must return to Ethereum before minting AIT. Custody allocations, restrictions and bridge security configuration are deployment inputs. |
| **AIT** | 18-decimal fungible token minted against locked MAX. Launch mint, burn, transfer and staking are on Ethereum; cross-chain AIT transfer is inactive. The proposed Genesis outstanding cap is 50,000 AIT. | AIT is not cash-redeemable, a stablecoin or a claim on Treasury principal. Buying AIT does not transfer someone else's MAX position. |
| **Merged position** | Each controller has one non-transferable active position containing remaining AIT debt and locked MAX. The displayed average is active MAX divided by active AIT debt. Partial AIT burns release proportional MAX into pending redemption; the final burn releases all residual MAX. | There is no active-position time lock. Every burn resets the **whole still-pending MAX balance** to a withdrawal time seven days after that burn. Staked AIT must be unstaked before burn. |
| **HWM and mint quote** | Global high-water mark is the greatest outstanding AIT debt ever reached and never falls on burn. Refill below it uses `R(HWM)`; a mint crossing it splits refill from new-peak curve cost. The complete charge rounds **once upward** to MAX wei. | Use [addendum §5's exact integer formula and vectors](./MAXSHOT_Decision_Gaps_and_Handoff_Addendum.md#5-confirmed-integer-mint-quote), not the prototype's floating-point illustration. |
| **AIT Earned Credit** | An eligible linked-wallet stake accrues during an approved funded term from confirmed Ethereum staking time. The Gateway automatically posts off-chain integer Credit grants at shared seven-day boundaries; each grant expires seven days after issue. | Unstaking immediately stops new accrual but preserves accrued, ungranted entitlement for the next batch. The term rate, approved catalogs and reserve are program inputs; no unfunded or perpetual entitlement is implied. |
| **Dollar balance and other Credits** | Dollar balance is user-funded USD from confirmed top-ups. Credits are separate usage buckets: AIT Earned Credit, Basic-chat and Premium subscription allowances, Free Credits and Referral Credits. | For eligible requests, earliest-expiring AIT Earned Credit spends before subscription allowances, then promotional Credits, then Dollar balance. Only subscription-funded text usage consumes subscription text windows. AIT Earned Credit is not another ERC-20. |
| **Vault AIT rewards** | Vault revenue buys existing AIT in the market; operations prepare manual Merkle distributions every 14 days for eligible depositors. | This AIT reward is separate from weekly Gateway AIT Earned Credit and does not mint AIT or retire position debt. |
| **Provider Tokens (PT)** | Possible later provider-specific instruments and PT/MAX markets, subject to binding rights and separate approvals. | PT ownership, price or trading does not affect launch compute routing. Do not build PT trading or token-weighted routing as part of the current Gateway handoff. |

The [feature requirements](./MAXSHOT_Feature_Requirements_PRD.md) summarize user journeys. The [decision addendum](./MAXSHOT_Decision_Gaps_and_Handoff_Addendum.md) owns confirmed exceptions to the read-only source, exact position transitions, mint math, staking/grant arithmetic and open release inputs. The [tokenomics companion](./MAXSHOT_Tokenomics_and_Flywheels.md) explains the economic flows; its proposed values are not launch approval. The [one-pager](./MAXSHOT_One_Pager.md) is a quick orientation, not the authority for an implementation detail.

## 3. People and system responsibilities

| Role | Responsibility |
| --- | --- |
| **Gateway customer / external-agent creator** | Funds the account, chooses an eligible model, may explicitly pin an offering when that selection is supported, sets scoped credential limits and inspects Usage. An external agent uses the same account and eligible Credit ledger as the UI. The current prototype demonstrates model choice and sample routing, but has no working provider-pin control. |
| **Linked wallet / position controller** | Signs Ethereum mint, stake, burn and withdrawal actions. One verified Ethereum staking wallet may link to one Gateway account; changing/unlinking is unavailable at launch. Wallet-only Vault withdrawal for an existing depositor must remain possible before Gateway account linking. |
| **Provider** | Supplies a model/version offering, capabilities, policies and rates for Maxshot to verify and admit. One admitted route suffices to publish a model; a second equivalent offering is used once to prove shared routing. |
| **Gateway services** | Must deliver a verified model catalog, qualification/routing, maximum-charge authorization, usage, customer and provider ledger reconciliation, verified wallet attribution, accrual from finalized staking events and automatic off-chain grants. Usage and support evidence must explain selected versus serving offering, rate, fallback, funding and final charge. Service boundaries, records, IDs and index design belong to engineering. |
| **Operations / finance / security** | Supply provider admission evidence, cost/health configuration, custody and bridge deployment values, funded Credit reserves, invoice reconciliation and release approvals. These are inputs and gates, not permission to invent product behavior. |

The repository is a **frontend prototype**, not the production Gateway backend or deployed contracts. Browser token actions mutate local sample state. ## 5. How an agent should continue the work

1. **Locate the owning rule.** Start with the handoff index and release matrix, then the relevant decision and B1–B5 acceptance document. The read-only token PRD still supplies requirements that later decisions have not superseded; the read-only marketing deck supplies context, not an implementation rule. Do not edit either source. Distinguish confirmed behavior from proposed economics and operational inputs.
2. **State the concrete task and success check.** For a UI change, name the screen and rule it must show. For implementation, name the relevant acceptance case and evidence required. Resolve real product ambiguity with the user; leave internal schema and routine engineering choices to the implementation team.
3. **Make a narrow change.** Keep the shared model catalog, Credit naming and authorized-maximum rules consistent across Providers, Chat, Studio, Credits and API. Follow [frontend/AGENTS.md](../frontend/AGENTS.md) for prototype work. Do not silently replace the existing Vault transaction flow or add a managed Agent product.
4. **Verify at the right boundary.** For prototype code, run `npm run build` in `frontend` and inspect the affected UI. For contracts or backend work, use the addendum's integer vectors and the applicable B1–B5 live proof. Clearly report what remains unverified when those systems are unavailable.
5. **Update the owning document when a decision changes.** Keep the handoff index and prototype map aligned; avoid creating another competing source of truth. Keep unrelated repository changes out of the work.

**Current state (15 November 2026):** The product requirements, design and labeled UI prototype are ready for scoped development handoff. B1–B5 have acceptance criteria, but their live Gateway, provider, Vault, wallet, contract and Credit-ledger proofs have not been verified in this repository. Deployment economics, legal/security approvals and provider/program configuration remain separate release gates.
